## 1. Project Overview

A cross-browser (Chrome/Edge MV3, Firefox MV3, Firefox for Android) WebExtension by Faisal Bhuiyan (GPL-3.0-or-later, `LICENSE.md`; `package.json` and readme match). It detects streaming video URLs (HLS `.m3u8`, DASH `.mpd`, MP4, bare `.ts`, …) on web pages through `webRequest` headers, DOM scanning and resource-timing, lists them in a floating ▶️ button/menu, the toolbar popup and a toolbar badge, and lets the user: share/open them in an Android player (explicit VLC / MX Player / mpv-android intents or the system chooser), copy the URL, play them in a bundled in-browser player (Vidstack or Shaka UI; touch-friendly, resume, faster parallel buffering), open them in a desktop player (VLC/mpv via protocol handler, VLC HTTP interface or a Python native-messaging host), or download them: as one MP4 by the built-in downloader page (HLS incl. TS/alt-audio/AES-128, DASH, plain files; desktop and Android) or with yt-dlp/ffmpeg through the native host. The page's Referer/Origin/User-Agent (and optionally cookies), detected subtitles (`.vtt`/`.srt`/`.ass`/TTML/YouTube XML, `<track>`; converted to WebVTT for the built-in players) and the chosen HLS quality variant are forwarded where the target supports them; a cleaned page title ("Show S01E02") names the stream everywhere. Stack: vanilla JS (no framework), esbuild bundling of Vidstack/hls.js/Shaka (+ Shaka UI), Python 3 for the native host, Node `node:test` + Playwright (Chromium desktop + phone emulation) + Selenium (Firefox) for tests. Maturity: small hobby project with a real test suite; Firefox release is on AMO (v1.4 published, v1.5/v1.6 not yet released).

### 2.2 Key architectural decisions
- **One codebase, two manifests**: `const browser = chrome` shim at the top of `background.js`, `content.js`, `popup.js`.
- **No remote code**: players are bundled locally with esbuild.
- **State in `storage.local`**: `settings`, `detectedStreams` (serialised `Map` tabId → streams), `detectedSubtitles`; cleared on `runtime.onStartup`. The map survives MV3 worker eviction.
- **Per-tab serialisation** (`runExclusive` in `background.js`): every mutation of a tab's list (add, analyse, clear, remove) goes through one promise chain, so concurrent detections cannot overwrite each other.
- **Navigation handling**: a `webRequest.onBeforeRequest` (`main_frame`) clears the tab's streams and records `pendingNav`; DOM scans from the *old* document (message or `executeScript` result) are dropped (`isStaleDocument`). The background tells the content script when it cleared (`streamsCleared`), and `getStreams` filters by `stream.pageUrl`, because browsers deliver `webRequest` events to the background asynchronously (a new page's content script can ask before the clear arrives; observed in Firefox).
- **Safety nets for missed requests**: the content script re-reads `performance.getEntriesByType('resource')` and pulls `getStreams` on load (the extension's listeners are not live in the first ~second after browser start / install; observed in Chromium).
- **Header forwarding**: `onBeforeSendHeaders` (with `extraHeaders` on Chromium, plain on Firefox) captures Referer/Origin/User-Agent/Cookie per `requestId`; stored on each stream as `headers` (cookie only if the setting is on). The built-in player tab is opened as `about:blank`, a `declarativeNetRequest` **session rule** (`tabIds:[tab]`, id `tabId+1`) sets Referer/Origin and, with "Forward cookies" on, Cookie for it, then the tab navigates to the player page. The rule is tab-scoped on purpose (hls.js/Shaka fetch segments from hosts that cannot be known in advance; per-URL 5 s rules rely on its own downloader announcing each request). It is removed when the tab closes or makes any `http(s)` top-level navigation (Chromium also reports navigations to our own `chrome-extension://` pages, which must not remove it).
- **Frames and workers**: the background DOM scan (`extractVideoSources`) runs in all frames; sources from a sub-frame get that frame's URL as Referer/Origin. `webRequest` events with `tabId -1` (a page's service worker) are attributed to a tab with the same origin as the request initiator (`tabForWorkerRequest`, active tab first); our own extension's requests match no tab.
- **`.ts` handling**: `.ts` stays a stream pattern (some sites serve bare `.ts`), but a `.ts` is hidden when it is a segment of a detected m3u8 (`isSegmentOf`: playlist's real segment directory, same file stem, or same non-root directory).
- **Native host is optional** but is the default external method (`desktopExternalMethod: 'native'`): `nativeMessaging` is an *optional* permission requested from the popup (needs a user gesture). Existing users keep the method they saved.
- **Protocol links** are built by `buildProtocolUrl` and percent-encoded by default (`protocolUrlFormat: 'encoded'`, `'raw'` keeps `vlc://https://…`); `handler.py` accepts encoded, raw and browser-mangled forms.

### 2.3 Data flow
1. **Network path**: `onBeforeSendHeaders` (remember headers) → `onHeadersReceived` → status filter (`isUsableStatus`: 4xx/5xx/204 ignored) → `classifyUrl(url, contentType, resourceType)` → `addSubtitle` or `addStream(…, typeHint)`. `classifyUrl` order: non-http(s) rejected → user **custom patterns** (override every built-in filter) → stream URL **embedded in a query parameter** (`/proxy.php?u=…m3u8`, unless the outer URL matches a skip pattern) → `shouldSkipUrl` → subtitle → `isStreamUrl`/`isStreamContent` → webRequest type `media` (non-audio). The DOM/resource-timing path (`ingestDomSources`) uses the same `classifyUrl`; the content script drops resource-timing entries whose `responseStatus` is ≥ 400.
2. **DOM path**: content script (MutationObserver, 1 s debounce; `<video>`, `<source>`, `<track>`, `[data-source]`, resource timing) → `videoSourcesFound` → `ingestDomSources`; background also scans on tab `complete`/activation via `scripting.executeScript`.
3. `addStream`: honours `enabled`, `maxStreams`, white/blacklist (substring on hostname), skips our player tabs/extension pages, dedups, hides playlist segments, stores `{url,name,displayName,type,quality,duration,pageTitle,pageUrl,headers}`, updates the badge, debounces (500 ms) `streamDetected` to the tab, then asynchronously `analyzeStream` (via `scheduleAnalysis`): m3u8 → duration (sum of `#EXTINF`), master playlist → variants + real quality + duration of the first variant that can be fetched (up to 3) + `segmentDir`; mpd → highest `height` + duration. The playlist request (`fetchText(url, stream.headers)`) gets the page's Referer/Origin (and Cookie with "Forward cookies") from a temporary DNR session rule (ids ≥ 1 900 000 000, `urlFilter: |url|`, `tabIds: [-1]`, removed after the fetch); a failed fetch is retried up to 3 times (after 3 s / 6 s, or when the page requests the playlist again); `forgetAnalyses` resets this when the tab's list is cleared.
4. **Actions** (content menu, popup, context menu, shortcut) → background `buildContext` (stream + headers + subtitles) → `runAction`: `browser` (the chosen engine; Shaka forced only for DASH) / `external` (protocol, `vlc_http` with `&option=http-referrer=…`, or native) / `download` / `copy`. Failures raise a notification.
5. **Native command** is built from a preset by executable name (mpv/vlc) or a user template (`{url} {referer} {ua} {title} {cookie} {sub}`); tokens with empty placeholders are dropped, `{sub}` repeats per subtitle.

Message types to the background: `videoSourcesFound`, `getStreams` (`tabId` from popup, `docUrl` from content), `getSettings`, `updateSettings`, `getStreamCount`, `openWebPlayer`, `openExternalPlayer`, `downloadStream`, `nativePing`, `saveFromPlayer` (only from our own pages: opens `download.html?url&title&subs&cache&vh&vbw&alang&autostart=1` with the player tab's session-rule Referer/Origin/Cookie copied to the new tab).

**Whole-video download data flow**: player page → `openPlayerCache` → engine hook (hls.js `fLoader` + `LEVEL_LOADED/SWITCHED`, `AUDIO_TRACK_*` → `setPlan`; Shaka scheme plugin + `variantchanged/adaptation/trackschanged` → `setPlan`) → `timeupdate/seeking` → `setPosition` → badge. Save → background `saveFromPlayer` (`partial` passed through) → download page opens the cache database read-only (with `partial=1` it lists the stored keys and passes `keep(uri, range)` to `downloadManifest`, which keeps each ref's playlist position for the AES-128 IV; file named "… (part).mp4") (`IdbStore.openExisting`), `cachedFetch` (keys `url` or `url|start-end`) for `downloadManifest`/`loadTextStream` and the same scheme plugin for its preview Shaka; reports `fromCache`/`fromNetwork`. Background → content: `streamDetected`, `streamsCleared`.

### 2.4 Native host protocol v2 (`native-host/host.py`)
Length-prefixed JSON on stdio. `{"action":"ping"}` → `{status:"ok",version:2,os,python,ytdlp,ffmpeg}`; `{"action":"launch","command":[exe,…]}` (a bare `command` key also works) → `{status:"launched",method:"direct"|"scheduler"}`; `{"action":"download",url,title,dir,headers}` → picks yt-dlp, else ffmpeg, runs in a new console. Errors reply `{status:"error",error}` and the host keeps serving. Windows launch: `Popen` with `DETACHED_PROCESS | CREATE_BREAKAWAY_FROM_JOB`; if the browser's job object forbids breakaway it falls back to a one-shot `schtasks` task running a generated `.bat` whose arguments are sanitised (`bat_quote`: `%`→`%%`, `"`→`'`, trailing `\` doubled).

## 4. Local Setup Guide

Prerequisites (VERIFIED on the audit machine): Node.js 24, npm 11, Python 3.9 (native host + host tests), Windows 11. Chromium tests use Playwright's Chromium (branded Chrome ≥137 ignores `--load-extension`); Firefox tests need Firefox + geckodriver (Selenium Manager downloads it).

1. Clone and install:
   ```
   git clone https://github.com/faisalbhuiyan3038/Stream-to-Android-Player-Extension.git
   cd Stream-to-Android-Player-Extension
   git checkout chrome-mv3-latest
   npm ci
   ```
2. (Only after editing `src/*.js`) rebuild bundles: `npm run build` (VERIFIED).
3. Pick the manifest: `npm run target:chrome` or `npm run target:firefox` (overwrites `manifest.json`).
4. Load unpacked: Chrome/Edge `chrome://extensions` → Developer mode → *Load unpacked* → repo root; Firefox `about:debugging#/runtime/this-firefox` → *Load Temporary Add-on* → `manifest.json`.
5. Native host (optional, desktop): Windows `native-host\install.bat [chromium-extension-id]` (Firefox is always registered; blank ID skips Chromium browsers), Linux/macOS `native-host/install.sh [id]`; restart the browser; popup → *External Player Integration* → *Native Messaging* → grant permission → *Test native host*.
6. Release zips: `npm run package` (plain copies) or `npm run release` / `release:chrome` / `release:firefox` (minified build in `dist/<target>/` + `releases/…-<target>-min.zip`; load `dist/<target>` unpacked to try it). For addons.mozilla.org, minified code needs the source code uploaded with the version.

### Environment variables
None required. Test-only: `E2E_NETWORK=1` (also play real public HLS/DASH streams), `E2E_NATIVE=1` (Firefox: launch a program through the installed native host), `HEADLESS=1`, `FIREFOX_BIN`, `PYTHON`.

| Item | Value |
|---|---|

### Troubleshooting
- Wrong manifest for the browser → rerun step 3.
- "nativeMessaging permission not granted" → popup → Native Messaging → *Grant Permission* (needs a click).

- **Add a web-player engine**: `src/` entry + HTML + esbuild script (+ `build` chain) + `EXTENSION_FILES` in `scripts/build-extension.js` + `PREBUILT` in `scripts/build-release.js` + `FILES` in `tests/e2e/stage.js` + `ENGINE_PAGES` (and `dashPageFor`) in `background.js` + both popup engine selects + `web_accessible_resources` in the three manifests.
- **Add a packaged file**: list it in `EXTENSION_FILES` (`scripts/build-extension.js`) and in `FILES` of `tests/e2e/stage.js` (the staged copy all browser tests load), and add it to the manifest if needed.
- **Version bump**: both `manifest.*.json` (and `manifest.json` via `npm run target:*`); `package.json` version is informational.

## 6. Known Issues & Technical Debt (prioritised)

1. **Android is unverified on a real device.** Layout and touch of the web players, download page, popup and in-page menu are covered by Chromium phone emulation only (`tests/e2e/mobile.test.js`); Firefox for Android itself has never run the extension here (device pending, TASKS.md note). No device test of intents, `package=` targeting, `S.subtitles_location`, popup share path (iframe `intent://` from a popup may not work on Firefox Android; `navigator.share` fallback), blob downloads from the download page, or memory use of long downloads. Web intents cannot carry headers or several subtitles.
2. **Firefox: extension pages are not scriptable through WebDriver**, so the built-in players (Shaka UI, subtitles, resume, faster buffering) and the download page are verified in Chromium only; the Firefox suite covers detection, the in-page UI and stream-link redirects. Firefox's minimum version stays 109, but `declarativeNetRequest` redirects need ~113 (stream links silently off on older versions) and the native-cue lift uses `:has()` (121+, cosmetic).
3. **Built-in downloader limits**: subtitles are embedded as plain-text tx3g (no styling); subtitle tracks carried inside fMP4 segments (wvtt/stpp) or CEA-608/708 captions are not offered; a sidecar subtitle whose timing assumes another start than the stream's first segment will be off by that amount; Chrome may ask once to allow "multiple downloads" when `.srt` files are saved too. Segments wait in IndexedDB (on disk), so RAM use stays at a few segments (measured 4.1 MB for a 61 MB file in Chromium); it needs free storage of about twice the file size until the file is saved (warned above 1 GB). If IndexedDB is unavailable (some private modes) it falls back to RAM (phones warned above 500 MB). Whether Firefox / Firefox for Android keep IndexedDB Blobs out of RAM the same way is not measured here. DRM and live streams are refused. A discontinuity that changes codec parameters (e.g. an ad with another resolution) is joined onto the first init segment and may play wrongly. DASH has no local test fixture (UNTESTED). Output is fragmented MP4 + `sidx` (not a progressive `moov` file); all players tried open and seek it, very old players might not. Relies on Shaka internals found by shape (`initSegmentOf`/`aesKeyOf`/`uriOf`) because the compiled build renames fields — re-check after Shaka upgrades (`getManifest()` itself warns it is not covered by semver).
4. **Chromium native messaging, context menu, shortcut, notifications, native download (yt-dlp/ffmpeg), `install.sh` and CI** are implemented but unexercised (see §3). CI was rewritten to run browser tests on `windows-latest` (H.264 fixtures) but has never run on GitHub.
5. **Startup race**: right after browser start/install, the extension's `webRequest` listeners are not live for ~1 s; the DOM/resource-timing safety net recovers stream URLs but not their captured request headers (falls back to the page URL as Referer) or content-type-only detections.
6. **Heuristics**: `VIDEO_PATTERNS`/`SKIP_PATTERNS` are still plain substrings (`manifest`, `/media/`, `analytics`, `pixel` …) — users can override them with custom patterns. A page whose title is only the site name gets no cleaned title and the UI falls back to the raw page title / file name. Iframes added after the page finished loading are only DOM-scanned again on tab activation (their network requests are still caught).
7. **Direct stream links**: the redirected player gets no Referer/Origin rule (nothing was detected on a page first), so CDNs that check the Referer fail there; open those from the page's stream list instead. `player.html` / `player-shaka.html` are web-accessible, so a web page can probe whether the extension is installed.
8. **Faster buffering**: only HLS/DASH (plain MP4 is streamed by the browser). Prefetching more than the player would have loaded uses more bandwidth when the user leaves early; 403/429 stop it for the session. Throughput-based ramp-up was measured against a throttled local server only.
9. **Players**: ArtPlayer page bundles hls.js + Shaka (~1.4 MB); manifest subtitle tracks are drawn natively by the engine (not by ArtPlayer's layer, so subtitle offset/size apply to page subtitle files only); ArtPlayer's built-in ArrowUp/Down etc. work only while it thinks it has focus (set at start; a click outside the player area — there is none on this page — would clear it). Vidstack 0.6 is legacy (no DASH → Shaka is forced for DASH). Shaka UI made `player-shaka.bundle.js` ~0.99 MB (was 0.77 MB); `download.bundle.js` adds 0.78 MB (Shaka again). For plain files (Shaka `src=` mode) native cues are lifted above the control bar only in Chromium. Quality memory is Shaka-only.
10. **Subtitle conversion**: ASS styling beyond italic/bold/underline/alignment (colours, fonts, positioning, karaoke) is dropped; TTML styling/regions are ignored; desktop and Android players still receive the original subtitle URL (they read SRT/ASS natively).
11. **Protocol handler**: the extension sends `vlc://<percent-encoded URL>` and ships `native-host/protocol-handler/handler.py`, but registration in the OS and the browser's first-use prompt are untested; macOS has no registration helper (needs an app bundle). `vlc_http` host/port are hard-coded, and its setup in VLC is easy to miss (see `docs/PROTOCOL_HANDLER.md`).
12. **Native host details**: Windows breakaway-vs-scheduler path is selected at runtime (reply field `method`) and not recorded by the tests; scheduler fallback leaves a `StreamPlayerLaunch` task and `%TEMP%\stream_player_launch.bat` (arguments sanitised but lossy: `"`→`'`). `firefox_manifest.json` in the repo holds a machine-specific path and is the file the Firefox registry key points to — do not reset it to a placeholder. The Chromium host manifest still needs the extension ID typed in (no pinned key).
13. **Cookies**: forwarded only when "Forward cookies" is on (to desktop players and to the built-in player/downloader via the header rule), but then stored unencrypted in `storage.local` with the stream record. `Sec-Fetch-*` / `Sec-CH-UA*` headers are not imitated; the page's own values are sent.
14. **Test flake**: the Firefox drag test still fails now and then (also on the original code); rerun once before suspecting a change. Odd environment fact found while testing: this Chromium build answers a fetch of exactly `/hls-real/key.bin` with an empty 204 (other names work), so the AES fixture key is `enc.key`.
15. **Dependencies**: production dependencies audit clean (VERIFIED 2026-11-06 `npm audit --omit=dev`: 0); dev dependencies report 2 issues (1 low, 1 high).
16. **Hygiene**: bundles (~2.3 MB of player/download bundles) and release zips are committed; test fixtures (~0.8 MB) are committed; mojibake in a few old comments; `backlog/*.git` misnamed. 
17. **Duplicated logic**: DOM source scan exists in `content.js` and in `background.js extractVideoSources`; settings defaults in three files (`background.js`, `popup.js`, `content.js`); `readSettings`/`isMobile` are repeated in the three page bundles.
18. **Whole-video download limits**: with it on, ABR is off (one quality, like FastStream; the quality menu still switches and the download follows; already downloaded segments of the old quality stay until the limit needs room). Background tabs: worker timers avoid Chrome's timer slowing, but a browser can still freeze or discard a background tab (Chrome Memory/Energy Saver, Android killing the browser) — then downloading stops until the tab is back; not reproducible in Playwright. Each player tab has its own cache, deleted when the tab closes (closing/reloading the player starts over). Save copies the cached segments into the download page's own store, so it needs about the cache size again (plus the saved file) on disk for a moment. Plain files need byte-range support (`206`), else they are not cached (normal browser streaming). hls.js AES-encrypted *init segments with byte ranges* get padded ranges from hls.js and miss the cache (fetched twice). Downloading the whole video uses more bandwidth than watching part of it.

## 6b. Store compliance
- 2026-11 Chrome Web Store warning (ref "Purple Potassium") on the live **v1.4**: `downloads` and `notifications` requested but unused. Valid: the v1.4 Chrome zip requested both, and the v1.4 code called neither. **v1.6 resolves it**: no `downloads` (files are saved through a Blob `<a download>` link, which needs no permission); `notifications` is used by `notify()` for failed actions. Every remaining permission has live call sites (audit in `permission-justification.md`). Deadline: an approved new draft within 30 days of the email. Don't add a permission without a call site plus a justification entry.
